# design: 기능 설계

## 설정
시작할 때 `<이 스킬 폴더>/../autoEnterEnter/references/settings.md`로 DOCS(문서 위치)·BASE(기준 브랜치)·RULES(규칙)·COMMIT(커밋 형식)을 정하고 한 줄로 알린다.

## 목표
`grill`로 정한 "무엇을 할지"를 "어떻게 짤지"로 옮긴다.
설계만 한다. 코드·문서 수정, 커밋, 서브 에이전트 실행은 하지 않는다. 구현 순서는 `plan-it`이 맡는다.

## 입력
- `grill`의 "확정한 것" 표가 대화에 있으면 그것을 쓴다.
- 없으면 이슈 본문(`gh issue view`, 읽기만)과 메모리에서 결정을 모아 보여 주고 확인받는다.
  범위(처리하는 것/처리하지 않는 것)가 비어 있으면 `grill`을 먼저 권한다.

## 시작 전에 직접 찾을 것 (묻지 않는다)
- 관련 코드, RULES의 규칙 문서, 메모리의 이전 결정
- 찾은 사실은 "확인한 사실"로 먼저 짧게 알린다. 문서끼리 어긋나면 고치지 말고 알리기만 한다.

## 지킬 제약 (항목 1 전에)
- 근거 순서: 규칙 → 머지된 코드 → 이슈 → 열린 PR(참고만). 부딪히면 앞의 것을 따른다.
- 이번 설계가 건드릴 파일 종류에 해당하는 RULES의 규칙과 관련 메모리를 **빠짐없이 전부** 적고 줄마다 출처를 단다.
- "이 밖에 꼭 지켜야 할 것이 있나요?"를 묻고, 답을 더해 확정한다.

## 항목 (이 순서대로 하나씩)
| # | 항목 | 담을 것 |
|---|---|---|
| 1 | 흐름 | 번호 단계 `[1] → [2] → ...` + `sequenceDiagram` |
| 2 | 모듈 간 통신·요청서 | 동기/비동기, 다른 팀에 넘길 요청서(제안) 초안 |
| 3 | 테이블 | 컬럼, PK/UK, 인덱스, `erDiagram` |
| 4 | 상태 | 상태 목록, 전이 조건, `stateDiagram-v2` |
| 5 | API | URL, 요청·응답, 권한, 오류 코드·HTTP 상태 |
| 6 | 중복 방지·동시성·트랜잭션 경계 | 중복 키, 잠금 방식, 트랜잭션이 어디서 시작하고 끝나는지 |
| 7 | 실패 처리·받아들인 위험 | 실패 지점별 처리, 일부러 받아들인 위험과 이유 |
| 8 | 대안 비교 | 고른 안, 버린 안과 버린 이유(트레이드오프) |
| 9 | 1차/2차 구현 | 지금 만들 것과 나중으로 미룬 것 |

해당이 없는 항목은 건너뛰지 말고 `해당 없음 — <이유>` 한 줄로 남긴다.

## 항목 하나 진행 방식
1. 초안(그림·표)을 먼저 보여 준다.
   초안의 바꿀 것마다 셋 중 하나로 표시한다.
   - 이슈 요구: 묻지 않고 반영 (이슈 #N)
   - 규칙·이슈 위반 수정: 묻지 않고 고치고 근거를 적음
   - **선택 사항**: 이것만 묻는다. "선택입니다"라고 밝히고 "해야 한다"로 쓰지 않는다
     (선택 사항을 해야 하는 일처럼 적으면 사용자가 고를 기회를 잃는다)
2. 그 안에서 정해야 할 결정을 `grill`의 질문 형식으로 **하나씩** 묻는다.
   (왜 묻나 / 숫자 예시 / 선택지와 추천 / 규칙·메모리 근거)
3. 답을 받으면 "정리: <결정 한 줄>"로 확인하고, 다음 결정이나 다음 항목으로 넘어간다.
4. 뒤 항목에서 앞의 결정과 부딪히는 게 나오면 넘어가지 말고 그 자리에서 짚는다.
- 동작이 바뀌지 않는 취향 문제는 묻지 않고 가까운 규칙대로 정한 뒤 끝에 알린다.

## 그림 규칙
- 기존 코드가 있는 부분은 코드를 읽고 그린다. 추측한 분기는 넣지 않고, 확인 못 한 부분은 그림 아래에 따로 적는다.
- Mermaid만 쓴다. 이모지와 색상 지정은 넣지 않는다.

## 다른 모듈
- 다른 모듈의 내부 구현은 묻지 않는다. 필요한 것은 "요청서(제안)"로 적고, 상대 팀의 답은 TODO(확인 필요)로 둔다.

## 용어
- 처음 정한 용어를 끝까지 쓴다. 새 용어가 생기면 `용어: <이름> = <뜻>` 한 줄로 남긴다.

## 끝낼 때
9개 항목이 다 정해지면 아래 문서를 대화창에 보여 주고 승인을 받는다.
승인하면 `DOCS/designs/<yyyy-MM-dd>-<이슈번호 또는 기능명>.md`에 저장한다.

    # <기능명> 설계
    - 근거 결정: <확정한 것 표 또는 이슈 링크>
    ## 지킬 제약
    ## 1. 흐름 … ## 9. 1차/2차 구현
    ## 용어
    ## 처리하지 않는 것
    ## 다른 팀 요청서
    ## 이슈 체크리스트 대조   (이슈 줄 → 설계 항목. 맡은 항목이 없는 줄은 "빠짐")
    ## TODO(확인 필요)
    ## 회의 안건 후보
    ## 변경 이력   (| 날짜 | 무엇을 | 이전 값 | 이유 | — 처음 만들 때는 비워 두고, 다시 고칠 때 한 줄씩 추가)

- Claude 문서, 메모리 저장, 이슈 댓글은 각각 사용자가 하라고 할 때만 한다.

## 하지 않는 것
- 코드·문서 수정, 커밋, 서브 에이전트 실행
- 질문 여러 개를 한 번에 쏟아내기
- 9개 항목 초안을 한 번에 다 쓰기
- 사용자가 메모리·CLAUDE.md에서 언급하지 말라고 정한 주제
