# plan-it: 설계를 구현 계획으로

## 설정
시작할 때 `<이 스킬 폴더>/../autoEnterEnter/references/settings.md`로 DOCS(문서 위치)·BASE(기준 브랜치)·RULES(규칙)·COMMIT(커밋 형식)을 정하고 한 줄로 알린다.

## 목표
확정한 설계를 "어떤 파일을, 어떤 시그니처로, 어떤 테스트로 확인하며, 어디서 커밋을 끊을지"로 옮긴다.
계획만 만든다. 코드 수정, 커밋, 서브 에이전트 실행은 하지 않는다.

## 입력
- `DOCS/designs/`의 설계 문서가 있으면 그것을 쓴다. 없으면 `grill`의 "확정한 것" 표를 쓴다.
- 둘 다 없으면 이슈 본문(`gh issue view`, 읽기만)에서 결정을 모아 확인받는다.
  설계가 필요한 크기(새 테이블·배치 단계·이벤트)면 계획을 쓰지 말고 `design`을 먼저 권한다.

## 순서 (각 단계에서 답을 받은 뒤 다음으로)
1. **바꿀 파일 목록**: 만들 파일과 고칠 파일, 각 파일이 맡는 일 한 줄. 공통 코드 재사용을 우선한다.
2. **지킬 제약**: 1의 파일 종류에 해당하는 RULES의 규칙과 관련 메모리를 **빠짐없이 전부** 적는다.
   골라서 빼지 않는다. 각 줄 끝에 출처(규칙 파일·메모리 이름)를 단다.
   그다음 "이 밖에 이번 작업에서 꼭 지켜야 할 것이 있나요?"를 묻고, 답을 더해 확정한다.
3. **사고 날 만한 경우**: 설계·결정에는 없지만 들어올 수 있는 입력·상황 후보를 최대 5개 적는다.
   (입력 → 기대 동작 → 맡을 테스트 이름) "더 넣을 경우가 있나요?"를 묻고, 확정된 것만 테스트로 단계에 붙인다.
4. **단계와 커밋 경계**: 아래 형식으로 쓴다.
5. **셀프 점검** 후 전체 계획을 보여 주고 승인을 받는다.
6. 승인하면 `DOCS/plans/<yyyy-MM-dd>-<이슈번호>.md`에 저장한다.

## 단계 하나의 형식

    ### N단계: <한 줄 제목>
    - 파일: 만들기 `경로` / 고치기 `경로`
    - 받는 것: <앞 단계에서 받아 쓰는 시그니처>
    - 넘기는 것: <뒤 단계가 쓰는 시그니처 — 이름, 파라미터, 반환 타입>
    - [ ] 구현: `ClassName.method(Type arg): ReturnType`
    - [ ] 테스트: `<RULES의 테스트 이름 규칙대로>` — 확인할 값 한 줄 (사고 날 만한 경우 번호가 있으면 함께)
    - [ ] 확인: `<레포의 테스트 명령>` → 통과   (예: `./gradlew test --tests …`, `npm test -- …`)

- 본문 코드는 쓰지 않는다. 실제 전/후 코드는 구현할 때 단계마다 보여 준다.
- 순서는 RULES에 테스트 순서 규칙이 있으면 그대로, 없으면 구현 → 테스트 → 통과 확인.
- 커밋 경계는 단계 사이에 한 줄로 적는다:
  `── 커밋 ①: <COMMIT 형식의 제목> (1~2단계) ──` 실제 커밋은 그 시점에 승인을 받은 뒤 COMMIT 형식으로 한다.

## 계획 문서 머리

    # #<이슈번호> <제목> 구현 계획
    - 목표: <한 문장>
    - 근거: <설계 문서 경로, 확정한 것 표 또는 이슈 링크>
    ## 지킬 제약
    ## 사고 날 만한 경우
    ## 단계
    ## 처리하지 않는 것
    ## TODO(확인 필요)

## 셀프 점검 (보여 주기 전에 혼자)
1. 결정 누락: 설계·확정한 것의 각 줄을 맡은 단계가 있는가
2. 이름 일치: 앞 단계의 "넘기는 것"과 뒤 단계의 "받는 것"의 이름·타입이 같은가
3. 빈 줄: "적절히 처리", "엣지 케이스 처리"처럼 아무것도 정하지 않는 줄이 없는가
4. 사고 날 만한 경우: 확정된 각 경우에 테스트가 붙었는가
5. 길이: 계획이 코드보다 길어지지 않았는가
6. 이슈 대조: 이슈 체크리스트의 각 줄을 맡은 단계가 있는가. 없으면 단계를 추가하거나,
   이슈가 후속으로 정한 줄이면 "이슈가 후속으로 명시"라고 적는다.
문제가 있으면 고친 뒤 보여 준다.

## 하지 않는 것
- 코드·문서 수정, 커밋, 서브 에이전트 실행
- RULES가 정하지 않은 순서(예: TDD) 강요, 단계마다 커밋
- DOCS 밖에 저장
- 질문 여러 개를 한 번에 쏟아내기
