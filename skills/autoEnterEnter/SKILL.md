# autoEnterEnter: 작업 시작 메뉴

## 목표
"이거 이거 하자"고 할 때마다 스킬이나 점검이 하나씩 빠지는 것을 막는다.
작업 종류를 고르면 정해진 순서표대로 진행한다. 순서표에 없는 단계를 끼워 넣거나 빼지 않는다.

## 시작
아래 메뉴만 출력하고 답을 기다린다.

    무엇을 할까요?
    1. 설계부터                — 이슈만 있거나 이슈도 없음
    2. 코드 작성               — 설계 문서(DOCS/designs)가 있음
    3. 코드 수정 (설계 없이)    — 이슈가 있고 설계가 필요 없는 작은 수정
    4. PR 마무리               — 구현이 끝남
    5. 코드 재수정             — 이미 만든 코드의 설계가 바뀜 (설계도 다시 수정, 없으면 만들기)
    6. 코드 리뷰               — 무엇이 어떻게 바뀌었는지 설명 + 결함 찾기 (고치지는 않음)

이슈 번호를 함께 말하면(예: "2 #12") 그 이슈로 시작한다.

## 공통 규칙
- **설정:** 메뉴를 고르면 먼저 `references/settings.md`(이 스킬 폴더 안)로 DOCS·BASE·RULES·COMMIT·PR을 정하고 한 줄로 알린다.
  이 문서의 `DOCS`, `BASE`, `RULES`, `COMMIT`, `PR`은 그렇게 정한 값이다.
- **단계 안내:** 단계를 시작할 때마다 한 줄로 알린다.
  `[메뉴 2 · ②/⑦] plan-it — 설계를 "어떤 파일을, 어떤 순서로, 무슨 테스트로" 만들지 단계 목록으로 바꾸는 단계예요.`
  `엔터 → 진행 / "멈춰" → 중지`
- **엔터로 넘어가는 것:** 단계 사이 이동만 해당한다.
- **엔터로 넘어가지 않는 것 (명확한 승인 필요):** 코드 반영(단계별 확인일 때), 커밋, 이슈 생성 등 GitHub에 쓰는 일, push.
- **다른 스킬 쓰기:** `grill`·`design`·`plan-it`·`run-plan`은 이 스킬 폴더 옆에 있다.
  `<이 스킬 폴더>/../<이름>/SKILL.md`를 읽고 그대로 따른다. 커밋은 COMMIT, PR 본문은 PR 설정대로 한다.
- **메뉴 안에서는 다음 단계를 권하지 않는다.** 순서표가 이어 준다.
- **근거 순서:** RULES의 근거 순서(규칙 → 머지된 코드 → 이슈 → 열린 PR은 참고만)를 따른다.
- **시작 점검 (모든 메뉴의 ①):** 세션이 레포 루트인지(`git rev-parse --show-toplevel`), 현재 브랜치.
  DOCS는 cd 하지 않고 전체 경로로 다룬다.
- **보고:** 원격 상태와 실행 결과를 확인한 것만 "됨"으로 쓰고, 못 한 것은 "확인 못 함"으로 쓴다.

## 메뉴 1. 설계부터
① 시작 점검
② 이슈 확인
   - 있음: 번호를 받는다.
   - 없음: `grill`로 무엇을 하고 무엇을 안 할지 맞춘다 → 이슈 본문 초안
     (`.github/ISSUE_TEMPLATE/`이 있으면 맞는 템플릿, 없으면 "배경 / 할 일 체크리스트 / 하지 않는 것")
     (쉬운 말, 일을 미룬 것처럼 읽히지 않게) → **승인 후** `gh issue create` → 번호를 받는다.
③ 이슈 체크리스트 표 (`grill`의 형식)
④ 근거 순서를 한 줄로 밝힌다
⑤ `grill` — 체크리스트에서 빠진 결정만 묻는다 (②에서 이슈를 만들었어도 짧게 다시)
⑥ `design`
⑦ `plan-it`
⑧ 마무리: 이슈 체크리스트 대조표(줄 → 설계 항목·계획 단계, 빠진 줄 표시), 메모리 저장 여부 묻기,
   "다음은 메뉴 2(코드 작성)" 안내

## 메뉴 2. 코드 작성 (설계가 있음)
① 시작 점검 — 브랜치가 이슈 브랜치가 아니거나 구현하지 않는 브랜치(BASE·main·master)면 BASE에서 새로 만들지 묻는다
   (브랜치 이름은 RULES에 규칙이 있으면 그것, 없으면 `<유형>/<이슈번호>`)
② 설계(`DOCS/designs/`)와 계획(`DOCS/plans/`)을 읽는다. 계획이 없으면 `plan-it`부터
③ 이슈를 다시 읽고 체크리스트 대조. 설계한 뒤 이슈가 바뀌었으면 먼저 알린다
④-0 진행 방식을 묻는다
    1. 단계별 확인 — 단계마다 실제 전/후 코드 + `// ◀ 설명`을 보여 주고 승인받은 뒤 반영, 커밋도 승인 후
    2. 자동 — `run-plan`으로 구현·단계 리뷰·마지막 3관점 리뷰까지 진행 (에이전트 약 <단계 수 + 5>개)
       자동 범위: 로컬 코드 수정·테스트·로컬 커밋만. push·PR·설정 파일·문서는 "변경 필요"로만 보고
④ 구현 → 테스트 → 통과 확인
⑤ 계획의 커밋 경계에서 COMMIT 형식으로 커밋 (파일 이름 지정, 커밋 후 `git log -1 --stat`)
⑥ 실제 앱으로 확인할 것이 있으면 실행해 확인. 못 한 것은 "확인 못 함"
⑦ 마무리: 이슈 대조표(줄 → 커밋).
   자동이었으면 장부의 Ruling 중 **설계와 다르게 정한 것**을 모아 보여 주고 맞는지 확인받는다. 확인 전에는 메뉴 4로 넘어가지 않는다.
   "다음은 메뉴 4(PR 마무리)" 안내

## 메뉴 3. 코드 수정 (설계 없이)
① 시작 점검
② 이슈를 읽고 체크리스트 표, 근거 순서
③ 크기 확인: 바꿀 파일이 3개 이상이거나 새 테이블·배치 단계·이벤트가 생기면 "메뉴 1(설계부터)로 갈까요?"
④ `grill` — 빠진 결정만
⑤ 진행 방식을 묻는다
    1. 단계별 확인 — 메뉴 2와 같음
    2. 자동 — 혼자 수정·테스트·로컬 커밋까지 하고, 끝에 `run-plan`의 리뷰 전용 모드로 3관점 리뷰 (에이전트 4~5개)
⑥ 수정 → 테스트 → 통과 확인
⑦ COMMIT 형식으로 커밋
⑧ 마무리: 이슈 대조표. "다음은 메뉴 4" 안내

## 메뉴 4. PR 마무리
① 시작 점검 — 이미 열린 PR이 있는지(`gh pr list --head <브랜치>`)
② 이슈 체크리스트 대조표(줄 → 커밋). 빠진 줄이 있으면 멈추고 알린다
③ 실행으로 확인한 것과 못 한 것을 나눈다. 못 한 것은 완료 조건에 체크하지 않는다
④ PR 설정대로 초안 — 아래 "PR 본문 형식"
⑤ 작성자 입장에서 다시 읽기: 일을 미룬 것처럼 읽히는 문장("범위 밖", "별도 이슈로" 나열),
   설명 없는 용어, 고친 뒤 사실이 아니게 된 문장
⑥ 초안을 보여 준다. push와 PR 생성은 요청할 때만

### PR 본문 형식
- 템플릿 섹션은 다 채우되, 펼친 부분은 짧게.
  - 개요: 무엇을, 왜 한두 줄
  - 작업 내용: 그림(흐름·테이블이 바뀌면 Mermaid, 아니면 "전 → 후" 표) + "바뀐 것 | 왜" 표
  - 참고 사항: 리뷰어가 확인할 점 3줄 이내. 용어는 처음 나올 때 괄호로 뜻
  - 완료 조건: 이슈 체크리스트 그대로, 확인한 것만 체크
- 긴 내용은 `<details><summary>…</summary>`로 접는다. `<summary>` 다음 줄은 비운다.
  파일별 변경, 테스트 목록, 설계 결정과 버린 대안, 실행 확인 기록, DB 초기화 같은 일부만 필요한 절차
- **고민 → 접근 → 해결:** 실제로 고민한 문제가 있을 때만 접기 안에 쓴다
  (문제 / 검토한 방법과 트레이드오프 / 고른 해결). 설계 문서의 대안 비교·변경 이력, 장부 Ruling, `grill` 결정에서 가져온다.
  없으면 억지로 만들지 않고 뺀다.
- 이슈가 원래 후속으로 정한 일은 다시 나열하지 않는다.

## 메뉴 5. 코드 재수정 (설계도 다시 수정, 없으면 만들기)
① 시작 점검 — 브랜치, 이미 열린 PR이 있는지(`gh pr list --head <브랜치>`)
② 왜 다시 고치나: 이유를 받는다(리뷰 지적, 이슈 변경, 직접 발견, 테스트 실패 등).
   줄 단위 리뷰 댓글은 붙여 넣어 받는다
③ 지금 상태 읽기: 이슈 체크리스트, 설계(`DOCS/designs/`), 계획(`DOCS/plans/`),
   이미 한 커밋(`git log BASE..HEAD`)
④ 설계 문서
   - 있음: `design` 형식으로 **바뀌는 항목만** 다시 맞춘다. 본문은 최신으로 고치고,
     끝의 "변경 이력" 표에 한 줄씩 추가한다
       | 날짜 | 무엇을 | 이전 값 | 이유 |
   - 없음: 지금 코드를 읽고 `design`의 9개 항목으로 설계 문서를 만든다.
     항목마다 "코드에서 읽음" / "이번에 정함"을 구분한다. 그다음 바뀌는 항목을 맞춘다
⑤ `plan-it` — 바뀐 부분만. 기존 계획 끝에 `## 재수정 N차` 섹션을 붙인다 (계획이 없으면 새로 만든다)
⑥ 진행 방식을 묻는다 — 메뉴 2와 같음 (단계별 확인 / 자동 `run-plan`)
⑦ 구현 → 테스트 → 통과 확인
⑧ 커밋 경계에서 COMMIT 형식으로 커밋
⑨ 마무리: 설계 전→후 요약(변경 이력 표), 이슈 대조표.
   자동이었으면 설계와 다르게 정한 Ruling 확인.
   열린 PR이 있으면 "메뉴 4로 PR 본문을 고칠까요?" 안내

## 메뉴 6. 코드 리뷰 (설명 + 결함 찾기, 고치지는 않음)
① 시작 점검 + 대상 정하기
   - 기본: 현재 브랜치의 `git diff BASE...HEAD` + 아직 커밋하지 않은 변경(`git diff HEAD`)
   - "6 #34"처럼 PR 번호를 주면 그 PR, 경로를 주면 그 경로
② 기준 읽기: 이슈 체크리스트(있으면), 설계(`DOCS/designs/`), 계획(`DOCS/plans/`)
③ **설명 (코드 둘러보기)** — 결함보다 먼저
   - 바뀐 흐름 그림 하나 (코드를 읽고 Mermaid로, 추측한 분기 없이)
   - 파일마다 "무엇을, 왜" 표
   - 핵심 로직(트랜잭션 경계, 동시성, 중복 방지, 이벤트 흐름)은 쉬운 말로, 다른 방법 대비 트레이드오프 한 줄
   - 용어는 처음 나올 때 괄호로 뜻
④ 결함 찾기 전에 묻는다: "혼자 볼까요, 에이전트도 띄워 3관점으로 볼까요?" + 대략 비용
   - 에이전트면 `run-plan`의 리뷰 전용 모드 (에이전트 4~5개)
⑤ 결함 목록: 심각도(높음/중간/낮음), `파일:줄`, 문제, 근거. "높음"은 검증된 것만
⑥ 항목마다 "고칠 것 / 그대로 둘 것(이유) / 선택 사항"으로 표시하고 사용자 확인
   (지적을 한꺼번에 빼거나 과하게 고치면 필요한 것까지 잃는다)
⑦ 저장: `DOCS/reviews/<yyyy-MM-dd>-<이슈번호 또는 브랜치>-review.md` (설명 + 결함 + 표시)
   나중에 "이거 어떻게 된 거야?"라고 물으면 이 파일을 먼저 읽고 답한다
⑧ 마무리: 고칠 것이 있으면 설계가 안 바뀌면 "메뉴 3으로 고칠까요?", 바뀌면 "메뉴 5로 고칠까요?"

## 하지 않는 것
- 메뉴 6에서 코드 고치기
- 순서표에 없는 단계 끼워 넣기, 순서표의 단계 건너뛰기 (건너뛸 땐 이유를 한 줄 남기고 사용자 확인)
- 승인 없이 GitHub에 쓰기, push
- 질문 여러 개를 한 번에 쏟아내기
